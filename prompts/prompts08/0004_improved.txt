Задача: подготовить MagicBorder к будущему портированию и сборке переносимых приложений под разные целевые платформы, зафиксировав совместимые версии Python и зависимостей.

Исходная формулировка:
"1. Необходимо подготовить проект к портрированнию на разные целевые платформы
2. Предполагается что дистрибуции подлежит полностью портируемое приложение включающее в себя все необходимые библиотеки
3. Требуется проверить версии всех библиотек на предмет наличия их под разные операционные системы. Это необходимо для предотвращения пересборки проекта под разные возможно не совсем совместимые версии библиотек. Прежде всего это касается библиотек для UI.
4. Необходимо обеспечить максимальную совместимость как на уровне исходного кода так и в последующей сборке портируемых приложений под целевую платформу.
5. Проведи эту работу, подбери необходимые версии и внеси соответствующие версии в проект.
6. На этом этапе пока не требуется реализация самих механизмов сборки под разные целевые платформы."

Контекст проекта:
- MagicBorder - локальное настольное приложение на Python и `PyQt5`.
- Проект использует `pyproject.toml` и `uv.lock`.
- Точка входа приложения:
  - `magicborder = "magicborder.main:main"`;
  - `magicborder-gui = "magicborder.main:main"`.
- В `pyproject.toml` уже есть зависимости:
  - `numpy`;
  - `opencv-python-headless`;
  - `Pillow`;
  - `PyQt5`;
  - `PyQt5-Qt5` с платформенными marker-условиями.
- Приложение использует растровую обработку изображений, canvas/UI на Qt, экспорт данных и локальные проектные JSON-файлы.
- Следующий этап будет посвящен созданию механизма сборки переносимых дистрибутивов. В этой задаче сам механизм сборки пока не реализовывать.

Цель:
- Подготовить зависимостную базу проекта так, чтобы будущая сборка переносимых приложений была воспроизводимой и максимально одинаковой на целевых платформах.
- Проверить, что выбранные версии прямых зависимостей имеют готовые wheel-дистрибутивы для целевых ОС и поддерживаемой версии Python.
- Зафиксировать в проекте совместимые версии или диапазоны версий, чтобы Linux/Windows/macOS-сборки не уехали на разные несовместимые наборы библиотек.
- Особое внимание уделить Qt-зависимостям (`PyQt5`, `PyQt5-Qt5`, `PyQt5-sip`), потому что UI-библиотеки чаще всего дают платформенные отличия.

Целевые платформы для аудита:
- Минимально обязательные:
  - Linux x86_64;
  - Windows x86_64.
- Желательно проверить и зафиксировать статус:
  - macOS x86_64;
  - macOS arm64;
  - Linux aarch64, если wheel-доступность зависимостей это позволяет.
- Если какая-то платформа не поддерживается выбранной зависимостью или требует отдельного решения, не скрывать это: указать ограничение в документе аудита.

Область работ:
- Проанализировать текущие прямые зависимости из `pyproject.toml`.
- Проверить wheel-доступность прямых и критичных транзитивных зависимостей по целевым платформам.
- Проверить совместимость с версией Python:
  - текущий `requires-python`;
  - фактически выбранную версию Python для сборок;
  - поддержку этой версии Python всеми критичными зависимостями.
- При необходимости уточнить `requires-python`, если текущий диапазон слишком широкий для переносимых сборок.
- При необходимости уточнить версии зависимостей в `pyproject.toml`:
  - зафиксировать верхние границы там, где риск несовместимых major/minor-обновлений высок;
  - сохранить платформенные marker-условия для Qt, если они нужны;
  - не делать бессмысленно жесткие пины без причины.
- Обновить `uv.lock` после изменения зависимостей.
- Добавить краткую документацию по выбранной матрице совместимости.

Рекомендуемый итоговый документ:
- Создать файл:
  - `doc/portable_dependency_matrix.md`
- В документе описать:
  - выбранную версию или диапазон Python для будущих portable-сборок;
  - список прямых зависимостей;
  - выбранные версии/диапазоны;
  - почему они выбраны;
  - какие платформы покрыты wheel-дистрибутивами;
  - какие ограничения или риски остаются.

Источники проверки:
- Использовать актуальные источники на момент выполнения задачи:
  - метаданные PyPI;
  - `uv lock`/`uv tree`;
  - официальные страницы пакетов, если PyPI-метаданных недостаточно.
- Не полагаться только на локально установленную среду.
- В документе указать дату проверки и кратко описать, откуда взяты сведения о wheel-доступности.

Требования к версиям и зависимостям:
- Не переводить проект с `PyQt5` на `PyQt6` или другой UI-фреймворк в рамках этой задачи.
- Не заменять `opencv-python-headless` на `opencv-python`, если для этого нет явной причины.
- Не добавлять упаковщики вроде `PyInstaller`, `Nuitka`, `cx_Freeze`, `Briefcase` или аналогов на этом этапе.
- Не добавлять runtime-зависимости, которые не нужны приложению сейчас.
- Если обнаружится, что какая-то зависимость плохо подходит для portable-сборки, сначала зафиксировать проблему и минимальное безопасное решение, а не переписывать функциональность приложения.
- Не ломать уже существующие тесты и запуск приложения.
- Сохранять `oiv_ampelometric_scales.json` в составе wheel, если он уже подключен через `tool.hatch.build.targets.wheel.force-include`.

Рекомендуемый подход к выбору Python:
- Проверить, какая версия Python дает лучший баланс:
  - наличие wheel-дистрибутивов для Qt, OpenCV, numpy и Pillow;
  - поддержка Linux/Windows/macOS;
  - стабильность для сборщиков portable-приложений на следующем этапе.
- Если проект сейчас допускает слишком широкий диапазон Python, например `>=3.10`, рассмотреть более явный диапазон вроде `>=3.10,<3.14` или другой обоснованный вариант.
- Не выбирать версию Python только потому, что она установлена локально.
- Если выбран конкретный Python для portable-сборок, записать это в документацию как рекомендацию, даже если `requires-python` остается диапазоном.

Рекомендуемый подход к Qt:
- Проверить связку:
  - `PyQt5`;
  - `PyQt5-Qt5`;
  - `PyQt5-sip`.
- Убедиться, что выбранная связка имеет wheels для целевых платформ.
- Проверить, нужны ли разные marker-условия для Windows и не-Windows платформ.
- Избегать смешивания несовместимых minor-версий PyQt/Qt runtime.
- Если на Windows доступна только более старая Qt-сборка, явно описать это и закрепить marker-условие в `pyproject.toml`.

Рекомендуемый подход к проверке:
- Перед изменениями сохранить понимание текущего состояния:
  - `uv tree`;
  - `uv lock --check`, если доступно;
  - текущие версии из `uv.lock`.
- После изменения зависимостей:
  - обновить lock-файл штатной командой `uv lock`;
  - запустить тесты проекта;
  - проверить импорт ключевых библиотек.
- Если возможно без полноценной сборки, проверить установку/резолв зависимостей для целевых платформ средствами `uv` или через анализ wheel-метаданных.

Команды проверки:
- Минимально:
  - `uv lock --check` или `uv lock`;
  - `uv run pytest`.
- Дополнительно, если уместно:
  - `uv tree`;
  - короткая проверка импортов `PyQt5`, `cv2`, `numpy`, `PIL`.

Не входит в задачу:
- Не создавать каталог `dist/`.
- Не писать скрипты сборки portable-приложения.
- Не настраивать PyInstaller/Nuitka/cx_Freeze.
- Не собирать `.exe`, AppImage, `.dmg`, `.app`, архивы или установщики.
- Не менять архитектуру приложения.
- Не переписывать UI.
- Не переносить проект на другой пакетный менеджер.
- Не удалять существующие OIV-файлы и настройки wheel-сборки.

Ожидаемые изменения в репозитории:
- При необходимости обновлен `pyproject.toml` с более аккуратными ограничениями версий.
- При необходимости обновлен `uv.lock`.
- Добавлен `doc/portable_dependency_matrix.md`.
- Изменения должны быть минимальными и объясненными.

Проверки перед завершением:
- `pyproject.toml` содержит совместимые и обоснованные ограничения прямых зависимостей.
- `uv.lock` согласован с `pyproject.toml`.
- В `doc/portable_dependency_matrix.md` есть:
  - дата аудита;
  - целевые платформы;
  - выбранная версия/диапазон Python;
  - таблица зависимостей;
  - комментарии по Qt;
  - ограничения и риски.
- Тесты проходят:
  - `uv run pytest`.
- Если какая-то проверка недоступна из-за сети или окружения, явно указать, что именно не удалось проверить и какие данные использовались вместо этого.

Критерии готовности:
- Проект подготовлен к следующему этапу упаковки: зависимости зафиксированы достаточно строго, чтобы будущие portable-сборки не получали случайно разные несовместимые версии.
- Есть понятный документ, по которому видно, какие платформы поддерживаются выбранной матрицей зависимостей и где остаются риски.
- Механизм сборки portable-дистрибутивов не реализован преждевременно.
