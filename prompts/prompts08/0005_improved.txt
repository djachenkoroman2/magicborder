Задача: создать в MagicBorder универсальный механизм сборки переносимых portable-приложений под разные целевые платформы.

Исходная формулировка:
"1. В проекте необходимо создать универсальный механизм для сборки портируемых версий приложения проекта.
2. Главная идея: универсальным должен быть не один бинарник для всех ОС, а единый сценарий сборки, который запускается на каждой целевой платформе и выдает одинаково устроенные артефакты.
...
В каталоге doc сделай подробную документацию для сборки портируемых приложений под разные платформы"

Контекст проекта:
- MagicBorder - настольное приложение на Python и `PyQt5`.
- Проект использует `pyproject.toml`, `uv.lock` и `uv`.
- Зависимости для portable-сборок уже подготовлены и описаны в:
  - `doc/portable_dependency_matrix.md`.
- Актуальный диапазон Python:
  - `>=3.11,<3.14`;
  - рекомендуемый Python для первых сборок: CPython `3.12.x`.
- Точки входа уже объявлены:
  - `magicborder = "magicborder.main:main"`;
  - `magicborder-gui = "magicborder.main:main"`.
- В wheel уже включаются:
  - `src/magicborder/assets`;
  - `oiv_ampelometric_scales.json`.
- В проекте есть runtime-данные, которые обязательно должны попадать в portable-сборку:
  - `src/magicborder/assets`;
  - `oiv_ampelometric_scales.json`.

Главная идея:
- Не пытаться создать один бинарник для всех ОС.
- Создать единый кроссплатформенный сценарий сборки, который запускается на каждой целевой платформе отдельно и выдает одинаково устроенные артефакты.
- Windows-сборка должна выполняться на Windows, Linux-сборка - на Linux, macOS-сборка - на macOS.
- Один и тот же проектный wrapper должен скрывать различия backend-а, путей, имен артефактов и включаемых данных.

Первый backend:
- Использовать `PyInstaller` как первый поддерживаемый backend.
- Причины:
  - хорошо подходит для PyQt5 desktop-приложений;
  - поддерживает сборку GUI-приложений с Python и зависимостями;
  - практичен для первого portable-результата.
- Не добавлять на этом этапе `Nuitka`, `cx_Freeze`, `Briefcase` как рабочие backend-и.
- При этом архитектуру wrapper-а сделать расширяемой, чтобы позже можно было добавить другие backend-и без переписывания CLI.

Целевые платформы:
- На первом этапе поддержать в структуре механизма:
  - `linux-x86_64`;
  - `windows-x86_64`;
  - `macos-x86_64`;
  - `macos-arm64`.
- Фактически собирать и проверять можно только текущую платформу, на которой выполняется задача.
- `linux-aarch64` не считать готовой целью из-за отсутствия wheel-покрытия PyQt5/PyQt5-Qt5, как описано в `doc/portable_dependency_matrix.md`.

Ожидаемая структура файлов:
```text
build_tools/
  portable_build.py
  backends/
    __init__.py
    pyinstaller.py
  manifests/
    magicborder.toml

doc/
  portable_build.md

dist/
  .gitkeep
```

Назначение файлов:
- `build_tools/portable_build.py`:
  - единая CLI-точка для сборки;
  - читает manifest;
  - определяет текущую платформу;
  - вызывает выбранный backend;
  - формирует стандартное имя артефакта;
  - выполняет базовые проверки результата.
- `build_tools/backends/pyinstaller.py`:
  - содержит backend-специфичную логику PyInstaller;
  - формирует команду `pyinstaller`;
  - подключает entrypoint, runtime-данные, имя приложения и GUI-режим;
  - не смешивает backend-логику с общим CLI.
- `build_tools/manifests/magicborder.toml`:
  - описывает приложение и сборочные настройки;
  - должен быть понятным и расширяемым.
- `doc/portable_build.md`:
  - подробная инструкция по сборке portable-приложений под разные платформы.
- `dist/.gitkeep`:
  - нужен только чтобы каталог `dist/` существовал в репозитории;
  - сами артефакты сборки должны игнорироваться git.

Manifest `build_tools/manifests/magicborder.toml` должен содержать:
```toml
[app]
name = "magicborder"
display_name = "MagicBorder"
version = "0.1.0"
entrypoint = "magicborder.main:main"
gui = true

[python]
requires = ">=3.11,<3.14"
recommended = "3.12"

[build]
backend = "pyinstaller"
output_root = "dist"

[[data]]
source = "src/magicborder/assets"
target = "magicborder/assets"

[[data]]
source = "oiv_ampelometric_scales.json"
target = "."
```

Допустимо изменить точный формат manifest-а, если это упростит реализацию, но он должен оставаться:
- текстовым;
- версионируемым;
- читаемым без запуска Python-кода;
- расширяемым для будущих backend-ов.

CLI:
- Основная команда:
  - `uv run python build_tools/portable_build.py`
- Поддержать аргументы:
  - `--manifest PATH` - путь к manifest-у, по умолчанию `build_tools/manifests/magicborder.toml`;
  - `--backend pyinstaller` - backend сборки, по умолчанию из manifest-а;
  - `--platform auto|linux-x86_64|windows-x86_64|macos-x86_64|macos-arm64`;
  - `--output-dir PATH` - корень для артефактов, по умолчанию из manifest-а;
  - `--clean` - очистить временную директорию backend-а перед сборкой;
  - `--skip-smoke-test` - не запускать smoke-test результата;
  - `--dry-run` - вывести план и команду backend-а без запуска сборки.
- Если пользователь указал платформу, отличную от текущей, команда должна завершаться понятной ошибкой, а не пытаться кросс-компилировать.
- Для `--dry-run` допустимо показывать план даже для чужой платформы, но явно писать, что фактическая сборка должна выполняться на целевой ОС.

Имена выходных артефактов:
- Формат:
  - `magicborder-0.1.0-linux-x86_64.tar.gz`;
  - `magicborder-0.1.0-windows-x86_64.zip`;
  - `magicborder-0.1.0-macos-x86_64.zip` или `.tar.gz`;
  - `magicborder-0.1.0-macos-arm64.zip` или `.tar.gz`.
- Внутри архива должна быть одна корневая папка:
  - `magicborder-0.1.0-<platform>/`.
- Внутри корневой папки должен лежать исполняемый файл/папка приложения и необходимые runtime-данные.

Требования к PyInstaller:
- Добавить `pyinstaller` как optional dependency, а не runtime dependency приложения.
- Рекомендуемый вариант в `pyproject.toml`:
```toml
[project.optional-dependencies]
build = [
  "pyinstaller>=6,<7",
]
```
- Сборка должна запускаться через:
  - `uv run --extra build python build_tools/portable_build.py`
- Для GUI-приложения использовать режим без консоли там, где это применимо:
  - `--windowed` / `--noconsole` для PyInstaller.
- Включить данные через `--add-data` с учетом разделителя путей:
  - `;` на Windows;
  - `:` на Linux/macOS.
- Не писать hand-made `.spec` на первом этапе, если хватает CLI-команды.
- Если `.spec` все же нужен из-за PyQt/OIV-данных, генерировать его контролируемо в build-каталоге, а не хранить как единственный источник истины без manifest-а.

Включаемые данные:
- Проверить, что в сборку попадают:
  - иконки и assets из `src/magicborder/assets`;
  - `oiv_ampelometric_scales.json`.
- Если текущий код ищет `oiv_ampelometric_scales.json` только в repo/root/wheel-layout путях, убедиться, что после PyInstaller-сборки файл находится в одном из ожидаемых путей.
- При необходимости аккуратно доработать поиск runtime-ресурсов, чтобы он работал:
  - из исходников;
  - из установленного wheel;
  - из PyInstaller portable-сборки.

Smoke-test:
- После сборки выполнить минимальную проверку результата:
  - проверить, что архив создан;
  - проверить, что архив не пустой;
  - проверить, что внутри есть ожидаемый исполняемый файл или app bundle;
  - проверить, что внутри есть OIV JSON;
  - проверить, что внутри есть assets.
- Не запускать GUI-приложение в полноценном интерактивном режиме как обязательный smoke-test, потому что CI/headless окружение может не иметь дисплея.
- На Linux можно опционально запускать импортный smoke-test до упаковки:
  - `uv run --extra build python -c "import PyQt5, cv2, numpy, PIL"`.

Документация `doc/portable_build.md`:
- Описать концепцию:
  - один сценарий, отдельная сборка на каждой ОС;
  - почему нет настоящей кросс-компиляции;
  - какие платформы целевые.
- Описать подготовку окружения:
  - Python 3.12.x;
  - `uv sync --frozen`;
  - `uv run --extra build ...`.
- Описать команды:
  - dry-run;
  - сборка текущей платформы;
  - очистка временных файлов;
  - smoke-test.
- Описать формат результата в `dist/`.
- Описать платформенные замечания:
  - Linux/glibc: собирать на самой старой поддерживаемой системе;
  - Windows: сборка на Windows, Qt runtime `PyQt5-Qt5==5.15.2`;
  - macOS: сборка на macOS, отдельно x86_64 и arm64;
  - Linux aarch64 пока не поддержан.
- Сослаться на:
  - `doc/portable_dependency_matrix.md`.

Git ignore:
- Убедиться, что реальные артефакты сборки не попадут в git.
- Если `.gitignore` отсутствует или не покрывает `dist/`, `.build/`, PyInstaller output, добавить минимальные правила.
- Разрешить оставить `dist/.gitkeep`:
```gitignore
dist/*
!dist/.gitkeep
build/
*.spec
```
- Если в проекте уже есть другие правила, не ломать их.

Ограничения:
- Не добавлять CI workflow на этом этапе, если пользователь отдельно не попросил.
- Не пытаться собрать Windows/macOS артефакты из Linux.
- Не добавлять `Nuitka`, `cx_Freeze`, `Briefcase` как зависимости сейчас.
- Не менять зависимости runtime-приложения без необходимости.
- Не менять логику приложения, кроме минимальной доработки поиска ресурсов для portable-режима.
- Не удалять существующие OIV-файлы, документацию и prompts.
- Не коммитить фактически собранные архивы, папки PyInstaller и временные build-output.

Рекомендуемые проверки:
- `uv lock --check`;
- `uv run pytest`;
- `uv run --extra build python build_tools/portable_build.py --dry-run`;
- если текущая платформа поддержана и окружение позволяет:
  - `uv run --extra build python build_tools/portable_build.py --clean`;
  - проверить, что в `dist/` появился архив;
  - проверить smoke-test результата.

Критерии готовности:
- В проекте есть единый CLI для portable-сборки.
- Сборочный manifest описывает приложение, backend и runtime-данные.
- PyInstaller backend умеет собрать portable-артефакт для текущей платформы.
- Артефакт имеет стандартное имя и структуру.
- OIV JSON и assets включаются в артефакт.
- Документация объясняет, как собирать под Linux, Windows и macOS.
- Реальные build-output файлы не попадают под версионирование.
- Тесты проекта продолжают проходить.
